# 产品需求文档：开播通知与 B 站动态推送优化

- 日期：2026-09-04
- 状态：待评审
- 关联文档：[bilibili-live-dynamic-notify-optimize-tech.md](bilibili-live-dynamic-notify-optimize-tech.md)（技术提案）、[bilibili-dynamic-subscription.md](bilibili-dynamic-subscription.md)（动态订阅初版方案）

## 背景

ZeroBot.Bilibili 插件现有两类自动推送能力：

1. **开播通知**：`LiveStatusSubscriber` 轮询订阅直播间的开播状态，状态变化时向订阅群推送「开/下播」文本消息。代码中已从直播信息里取出了封面图（`info.UserCover`）并构建出 `image` 变量，但该变量**从未被传入消息发送调用**，且其构建方式 `Enumerable.Repeat(segment, 0)` 产出的是一个空序列——封面图实际上从未发出过。
2. **动态推送**：`DynamicSubscriber` 轮询订阅用户的最新动态，`DynamicMessageBuilder` 将动态渲染为文本+图片消息推送到订阅群。当前推送消息缺少发布人信息，群成员收到消息时无法直观知道是谁发的动态；转发动态场景下，消息中附带的链接未标明是原动态还是转发动态，且只有一条链接，无法回溯转发动态本身。

## 需求

### R1：开播通知携带直播间封面图

开播/下播通知消息在文本段落之后追加直播间封面图（`info.UserCover`）：

- 当 `UserCover` 为非空字符串时，下载并转换图片段，追加到消息最尾；
- 当 `UserCover` 为空或白字符串时，不追加图片，行为与现状一致；
- 文本内容（`{开/下}啦~\n{标题} {链接}\n{时长}`）、@全体成员逻辑、发送目标群均不变。

### R2：动态推送开头标明发布人

每条动态推送消息的开头增加一个文本段落：

```
{发布人} 发布了新动态
```

- 「发布人」取动态数据中的作者昵称（B 站动态 item 的 `modules.module_author.name`）；
- 若动态数据中缺失作者信息，回退使用该订阅的 B 站用户 UID（mid）；
- 该段落对所有动态类型生效（图文、纯文字、转发等；直播推荐动态本就被 `DynamicSubscriber` 跳过，不受影响）。

### R3：转发动态链接标注与补全

转发动态（`DYNAMIC_TYPE_FORWARD`）推送消息中需包含**两条地址**：

1. **转发动态自身的地址**：转发动态可能没有 `jump_url`，缺失时按规则拼接 `https://www.bilibili.com/opus/{dynamicId}`；
2. **原动态的地址**：在现有原动态链接前加前缀「原动态：」，例如 `原动态：https://www.bilibili.com/opus/xxxx`。

非转发动态的链接展示保持不变（无前缀、按现有 `jump_url` 逻辑）。

## 验收标准

| # | 场景 | 预期 |
|---|------|------|
| 1 | 订阅直播间开播 | 群内收到「开啦~」文本 + 直播间封面图 |
| 2 | 订阅直播间下播 | 群内收到「下啦~」文本（含本场直播时长）+ 封面图 |
| 3 | 直播间无封面（`UserCover` 为空） | 消息仅文本，不报错 |
| 4 | 订阅用户发布普通图文动态 | 消息首段为「{昵称} 发布了新动态」，后续为动态正文与图片 |
| 5 | 订阅用户转发动态 | 消息首段为「{昵称} 发布了新动态」；消息中含转发动态自身地址与带「原动态：」前缀的原动态地址，共两条 |
| 6 | 转发动态无 `jump_url` | 转发动态自身地址为 `https://www.bilibili.com/opus/{dynamicId}` 拼接结果 |
| 7 | 动态数据缺失 `module_author` | 首段发布人显示为订阅的 mid，不报错 |

## 非目标

- 不改动订阅/取消订阅指令（`/B站动态:*`、直播订阅相关指令）的交互与权限；
- 不改动直播推荐动态（`DYNAMIC_TYPE_LIVE_RCMD`）的跳过策略；
- 不改动配置结构（`BilibiliOptions`）与轮询节奏；
- 不调整动态正文的富文本渲染与图片排列顺序。
